# 로드맵: 재방문 장치와 정책 정보

작성일: 2026-10-15. 현재 코드(정적 GitHub Pages, 로그인 없음, 관심 목록은 localStorage, 해시 라우팅, 방문 분석 없음)를 기준으로, AWS에 작은 API 서버를 추가하는 것을 전제로 한 작업 계획이다. 사용자 수·행동 데이터로 검증하기 전의 가설이며, 기간은 순서를 정하기 위한 대략치이고 확정 견적이 아니다.

## 제품 방향

서울·경기에서 매수나 이사를 준비하며 후보 단지를 반복 확인하는 사람을 첫 핵심 사용자로 삼는다. 핵심 가치는 "내가 보는 단지와 지역에 무엇이 바뀌었는지, 후보끼리 어떻게 다른지 빠르게 확인한다"이다.

첫 방문 → 관심단지·평형 저장 → 변화 확인 → 후보 비교 → 다음 변화 때 알림을 받고 재방문하는 흐름을 만든다. 실거래는 신고 지연이 있고 단지별 거래도 드물므로 주간 확인을 기본으로 하되, 매일 갱신되는 변화와 월간 지역 흐름도 제공한다.

## 원칙

- 조회 화면은 지금처럼 정적 파일로 제공하고, 서버는 상태가 필요한 기능(측정, 관심 목록 동기화, 개인 알림, 거래 이력)에만 쓴다. 서버가 멈춰도 조회·관심 저장(브라우저)은 동작해야 한다.
- 로그인 없이 쓰는 구조를 유지한다. 서버에 두는 것은 무작위 코드에 묶인 관심 목록과 알림 수신처뿐이고, 이름·전화번호·이메일은 받지 않는다(이메일 알림 도입 전까지).
- 재방문 장치는 실제로 관측된 변화(새 거래, 신고가, 국면 변화, 새 정책)부터 알린다. "급등 알림" 같은 자극적인 장치는 만들지 않는다. 예측은 지금처럼 실험 표시와 검증 기준을 유지한다.
- 정책은 날짜와 원문만 보여 주고 "정책 때문에 올랐다/내렸다" 같은 인과 해석은 하지 않는다.
- 한 번에 핵심 흐름 하나씩 바꾸고 효과를 확인한다.

## 이미 있는 기반

- 로그인 없는 지역 좋아요·관심단지 저장, 지역·단지 검색.
- 관심단지의 새 거래·신고가 배지, 주력 평형 가격 비교 차트.
- 실거래·전세가율·거래량·주간지수·실험적 예측.
- GitHub Pages 정적 배포와 매일 데이터 갱신(GitHub Actions).
- 로컬 개발용 `server.js`(조회 API). 운영 서버로 쓰지 않으며 새 API와는 별개다.

## 현재 빈틈

1. 방문 분석이 없어서 재방문율과 개선 효과를 알 수 없다.
2. 관심단지의 새 거래 표시는 사이트를 열어야만 보인다. 사이트 밖에서 알리는 수단이 없다.
3. 관심 목록이 브라우저에만 있어서 저장소를 지우거나 기기를 바꾸면 사라진다.
4. 해시 라우팅이라 지역·단지 페이지가 검색에 따로 노출되지 않고, 공유 미리보기도 모든 페이지가 같다.
5. 새 거래 판정 기준(`seen`)이 마지막 **계약일**이라서, 계약은 그 전에 했지만 늦게 신고된 거래가 새 거래에서 빠진다 (`public/app.js`의 관심단지 화면). 배포 거래 포맷에는 최초 관측 시점도 없고, 빌드가 쓰는 `actions/cache`는 지워질 수 있어 이력을 쌓아 둘 곳이 없다.
6. 첫 방문자에게 무엇부터 보면 되는지 안내가 없고, 관심단지는 평형 없이 단지 단위로만 저장된다.

## 서버 구성

| 구성 요소 | 선택 | 이유 |
|---|---|---|
| 리전 | `ap-northeast-2`(서울) | 사용자와 가깝고 국내 저장 |
| API | API Gateway HTTP API + Lambda(Node 20) | 트래픽이 적은 동안 비용이 사용량에 비례. 기존 코드와 같은 언어 |
| 저장소 | DynamoDB(동기화 목록·알림 구독·측정 집계), S3(거래 이력·변화 파일) | 서버 관리 없음. DynamoDB 시점 복구, S3 버전 관리로 백업 |
| 데이터 빌드 | 지금처럼 GitHub Actions | 첫 수집이 1~2시간이라 Lambda 15분 제한에 맞지 않음. Actions는 OIDC로 받은 임시 역할로 S3에 접근(장기 키 없음) |
| 알림 발송 | S3에 `changes.json`이 올라오면 실행되는 Lambda | 빌드와 발송을 분리해 발송 실패가 배포를 막지 않게 함 |
| 비밀값 | SSM Parameter Store | 텔레그램 봇 토큰, 웹 푸시 VAPID 키 |
| 배포 정의 | AWS SAM(코드로 관리) | 스택 하나로 재현·삭제 가능 |
| 프런트 | GitHub Pages 유지. 9번(정적 페이지)에서 S3 + CloudFront 이전 검토 | 지금은 옮길 이유가 없음 |

- 비용은 지금 규모에서 월 수 달러 수준으로 예상하지만 사용량을 보고 확인한다. AWS Budgets 알림(예: 월 $20)을 첫 작업에 포함한다.
- API는 Pages 출처만 CORS 허용, API Gateway 요청 제한, 요청 크기·관심 목록 개수 상한을 둔다.
- 모니터링: Lambda 오류율·발송 실패를 CloudWatch 알람으로 받는다. 서버 장애 시 프런트는 동기화·알림 기능만 숨기고 나머지는 그대로 보여 준다.

## 세부 사항

### 2. 측정

이벤트: 검색, 단지 조회, 관심 저장, 변화 확인, 후보 비교, 공유 링크 열기, 알림 연결·해지, 알림에서 들어온 방문, 재방문. 검색 원문과 상세 관심 목록은 수집하지 않는다.

- 브라우저마다 무작위 기기 ID(`crypto.randomUUID`)를 localStorage에 만들어 이벤트와 함께 보낸다. 쿠키·IP 저장·외부 분석 도구는 쓰지 않는다.
- 서버는 기기별로 첫 방문일·활성화일·방문한 주를 한 행에 갱신하고, 매일 집계 Lambda가 코호트 표를 만든다. 원본 이벤트는 90일 뒤 자동 삭제(DynamoDB TTL)하고 집계만 남긴다.
- 개인정보처리방침에 기기 ID의 목적·보관 기간과 "이 기기 기록 삭제" 방법을 밝힌다.

지표:

- **활성화**: 첫 방문 후 24시간 안에 관심단지를 저장하고 그 요약을 확인한 기기 비율. 6번 이후에는 평형 저장까지 포함한다.
- **핵심 재방문**: 활성화한 기기 중 다음 주(활성화 후 7~13일)에 관심단지 변화나 후보 비교를 확인한 비율. 28~34일 구간도 따로 잰다. 정확히 7일째 방문하는 지표와 구분한다.
- **변화 확인**: 새 거래가 있는 관심 사용자 중 변화 상세를 확인한 비율.
- **알림 효과**: 알림 연결 비율, 알림 발송 후 24시간 안 방문 비율, 해지율.
- **보조 지표**: 화면 종류별 조회, 비교 완료, 공유 링크 수신자의 관심 저장, 데이터 오류 제보.

첫 2주를 기준선으로 삼고 목표치를 정한다. 관심단지 수, 새 거래 유무, 알림 연결 여부, 모바일/데스크톱별로 나눠 본다. 동기화 코드를 쓰는 사람은 여러 기기를 한 사람으로 묶어 볼 수 있지만, 나머지는 기기 단위라 기기 변경·저장소 삭제 시 재방문이 낮게 나온다. 트래픽이 적은 동안은 A/B 수치만으로 결론 내리지 않고 실제 사용 관찰과 함께 평가한다. 코호트 정의는 [Amplitude의 리텐션 분석](https://www.amplitude.com/docs/analytics/charts/retention-analysis/retention-analysis-build)을 참고했으며 해당 제품 도입을 전제하지 않는다.

검증할 가설:

- 첫 방문 안내가 관심 저장을 늘린다.
- 변화 요약이 다음 주 확인을 늘린다.
- 개인 알림이 다음 주 확인을 늘리고, 해지율은 낮게 유지된다.
- 같은 평형 비교가 후보 재확인을 늘린다.

### 3. 정책 자료 형식

```json
{
  "id": "2026-xx-loan",
  "announced": "2026-xx-xx",
  "effective": "2026-xx-xx",
  "ended": null,
  "title": "…",
  "category": "대출 | 규제지역 | 토지거래허가 | 세제 | 공급",
  "regions": ["all"],
  "summary": "한두 줄 요약",
  "source": "정책브리핑·국토부·금융위 보도자료 URL"
}
```

- 발표일과 시행일을 구분한다. 차트 마커는 발표일 기준으로 표시한다.
- 해제·변경된 정책은 지우지 않고 `ended`를 채워 이력으로 남긴다.
- 페이지에 "요약은 참고용, 정확한 조건은 원문 확인" 안내와 마지막 수정일을 표시한다.
- 새 정책 후보는 정책브리핑·보도자료 RSS로 모을 수 있지만, 사람이 확인한 뒤 PR로 추가한다.
- 초기 내용: 최근 3~5년 주요 정책 초안을 공식 출처 기준으로 만들고 날짜·대상 지역을 검토한다.

### 4. 새 거래 판정 보완

- 브라우저의 계약일 비교 대신, 빌드에서 이전 이력 대비 새로 들어온 거래를 계산하고 최초 관측 이력을 유지한다. 최초 관측 시점은 신고일과 다르므로 화면에는 "새로 확인된 거래"로 표시한다.
- 이력은 S3(버전 관리 켬)에 두고 빌드 시작 때 읽어 끝날 때 다시 쓴다. 읽지 못하면 그날은 변화 없음으로 배포하고 다음 빌드에서 다시 시도한다(이력을 새로 만들지 않음). 잘못 쓴 이력은 이전 버전으로 되돌린다.
- 데이터 공급원의 거래 식별자를 먼저 확인한다. 매매 자료에 단지 고유번호가 없으므로, 없으면 단지·계약일·면적·층·금액으로 비교하되 조건이 같은 실제 복수 거래는 개수로 보존한다. 단지명 정규화(`canonicalKey`)를 거친 키를 쓴다.
- 처음 이력을 만들 때 기존 거래 전체를 새 거래로 표시하지 않는다.
- 취소·정정은 정확히 연결할 근거가 없으면 추가·삭제로만 표시하고 정정으로 단정하지 않는다.
- 반영 범위의 한계: 실거래는 최근 2개월만 다시 받으므로(`lib/molit.js`), 그보다 오래된 거래의 해제·정정은 잡히지 않는다. 화면에 이 범위를 밝히고, 재조회 기간을 늘릴지는 API 호출 한도를 보고 정한다.
- 기존 사용자 전환: 브라우저의 `seen`(마지막 계약일)은 전환 시 버리고, 전환 후 첫 방문 시점의 이력 기준으로 다시 시작한다. 전환 첫날 늦은 신고가 한꺼번에 새 거래로 뜨지 않게 한다.
- 검증 사례: 늦은 신고, 같은 계약일, 정정, 취소, 중복 수집, 이력 읽기 실패.

### 5. 동기화 코드

- 코드는 128비트 무작위 값이고, 서버에는 해시만 저장한다. 코드를 아는 사람은 목록을 읽고 고칠 수 있으므로 링크 공유 주의 문구를 표시하고, 재발급하면 이전 코드는 무효가 된다.
- 동기화 데이터에 형식 버전을 둔다. 항목마다 수정 시각을 두고 삭제는 삭제 표시로 남겨, 여러 기기에서 고친 내용을 항목 단위로 병합한다(같은 항목은 나중 수정이 이김).
- 브라우저 목록이 먼저 저장되고 서버는 나중에 맞춘다. 오프라인·서버 장애 때도 저장은 실패하지 않는다.
- 1년간 접근이 없는 코드와 목록은 삭제하고, 사이트에서 즉시 삭제할 수 있게 한다.

### 7. 개인 알림

- 연결: 사이트에서 "텔레그램으로 받기"를 누르면 일회용 토큰이 담긴 `t.me/<봇>?start=<토큰>` 링크를 연다. 봇이 토큰을 받아 대화 ID를 동기화 코드에 묶는다. 토큰은 10분 뒤 만료된다.
- 발송: `changes.json`이 올라오면 발송 Lambda가 구독별로 관심단지·평형의 변화를 모아 한 메시지로 보낸다. 변화가 없으면 보내지 않는다. 하루 1회 상한, 밤 시간 발송 금지, 같은 변화 중복 발송 방지(발송 기록).
- 메시지에는 단지·평형·금액·계약일과 사이트 링크만 넣고, 예측이나 "급등" 같은 표현은 넣지 않는다.
- 해지: 봇 `/stop`, 사이트 해지 버튼, 봇이 차단되면(발송 오류) 구독을 자동 삭제한다.
- 텔레그램 대화 ID와 웹 푸시 구독 정보는 개인정보로 다루고 개인정보처리방침에 목적·보관 기간을 적는다. 해지 즉시 삭제한다.
- 카카오톡 알림톡은 사업자 등록과 건당 비용이 필요해 이용 규모를 본 뒤 검토한다. 이메일(SES)은 도메인 인증과 발송 한도 해제가 필요해 13번으로 둔다.

## 후순위

전국 확대, 커뮤니티, 예측 모델 추가, 유료화, 선택적 계정(이메일·소셜 로그인)은 관심 저장과 반복 확인이 검증된 뒤 판단한다. 계정은 동기화 코드 사용량과 요청을 보고 도입하며, 기존 동기화 코드 목록을 계정으로 옮기는 기능을 지원한다.
