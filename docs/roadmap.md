# 로드맵: 재방문 장치와 정책 정보

작성일: 2026-10-15. 현재 코드(정적 GitHub Pages, 로그인 없음, 관심 목록은 localStorage, 해시 라우팅, 방문 분석 없음)를 기준으로, AWS에 작은 API 서버를 추가하는 것을 전제로 한 작업 계획이다. 사용자 수·행동 데이터로 검증하기 전의 가설이며, 기간은 순서를 정하기 위한 대략치이고 확정 견적이 아니다.

갱신: 2026-10-25. 1~5번 완료, 6번(텔레그램 알림)은 건너뛰기로 했다. 매매/전세 보기 분리(5-1번)를 새로 넣고 1단계까지 완료했다(측정 버전 4 배포). 1차 점검(2026-11-14 이후)을 기다리는 동안 관심 저장·재방문 흐름을 건드리지 않는 9번(정책 1차)을 먼저 했다. 다음은 1차 점검이다.

## 제품 방향

서울·경기에서 매수나 이사를 준비하며 후보 단지를 반복 확인하는 사람을 첫 핵심 사용자로 삼는다. 핵심 가치는 "내가 보는 단지와 지역에 무엇이 바뀌었는지, 후보끼리 어떻게 다른지 빠르게 확인한다"이다.

첫 방문 → 관심단지·평형 저장 → 변화 확인 → 후보 비교 → 다음 변화 때 알림을 받고 재방문하는 흐름을 만든다. 실거래는 신고 지연이 있고 단지별 거래도 드물므로 주간 확인을 기본으로 하되, 매일 갱신되는 변화와 월간 지역 흐름도 제공한다.

## 원칙

- 조회 화면은 지금처럼 정적 파일로 제공하고, 서버는 상태가 필요한 기능(측정, 관심 목록 동기화, 개인 알림, 거래 이력)에만 쓴다. 서버가 멈춰도 조회·관심 저장(브라우저)은 동작해야 한다.
- 로그인 없이 쓰는 구조를 유지한다. 서버에 두는 것은 무작위 코드에 묶인 관심 목록과 알림 수신처뿐이고, 이름·전화번호·이메일은 받지 않는다(이메일 알림 도입 전까지).
- 재방문 장치는 실제로 관측된 변화(새 거래, 신고가, 급등, 국면 변화, 새 정책)를 알린다. 급등 알림도 이미 신고된 거래와 공개 지수로만 판정하고(세부 사항 3-1), 근거 숫자를 함께 보여 준다. "더 오른다"는 예측이나 매수를 권하는 표현은 쓰지 않는다. 예측은 지금처럼 실험 표시와 검증 기준을 유지한다.
- 정책은 날짜와 원문만 보여 주고 "정책 때문에 올랐다/내렸다" 같은 인과 해석은 하지 않는다.
- 한 번에 핵심 흐름 하나씩 바꾸고 효과를 확인한다.

## 이미 있는 기반

- 로그인 없는 지역 좋아요·관심단지 저장, 지역·단지 검색.
- 관심단지의 새 거래·신고가 배지, 주력 평형 가격 비교 차트.
- 실거래·전세가율·거래량·주간지수·실험적 예측.
- GitHub Pages 정적 배포와 매일 데이터 갱신(GitHub Actions).
- 로컬 개발용 `server.js`(조회 API). 운영 서버로 쓰지 않으며 새 API와는 별개다.

## 현재 빈틈

작성 시점(2026-10-15) 기준이다. 1·3·5·6은 해결됐고(괄호 안 작업 번호), 2·4가 남았다.

1. (해결: 2번) 방문 분석이 없어서 재방문율과 개선 효과를 알 수 없다.
2. (남음: 8번 웹 푸시) 관심단지의 새 거래 표시는 사이트를 열어야만 보인다. 사이트 밖에서 알리는 수단이 없다.
3. (해결: 5번) 관심 목록이 브라우저에만 있어서 저장소를 지우거나 기기를 바꾸면 사라진다.
4. (남음: 11번) 해시 라우팅이라 지역·단지 페이지가 검색에 따로 노출되지 않고, 공유 미리보기도 모든 페이지가 같다.
5. (해결: 3번) 새 거래 판정 기준(`seen`)이 마지막 **계약일**이라서, 계약은 그 전에 했지만 늦게 신고된 거래가 새 거래에서 빠진다 (`public/app.js`의 관심단지 화면). 배포 거래 포맷에는 최초 관측 시점도 없고, 빌드가 쓰는 `actions/cache`는 지워질 수 있어 이력을 쌓아 둘 곳이 없다.
6. (해결: 4번) 첫 방문자에게 무엇부터 보면 되는지 안내가 없고, 관심단지는 평형 없이 단지 단위로만 저장된다.

## 서버 구성

| 구성 요소 | 선택 | 이유 |
|---|---|---|
| 리전 | `ap-northeast-2`(서울) | 사용자와 가깝고 국내 저장 |
| API | API Gateway HTTP API + Lambda(Node 24) | 트래픽이 적은 동안 비용이 사용량에 비례. 기존 코드와 같은 언어 |
| 저장소 | DynamoDB(동기화 목록·알림 구독·측정 집계), S3(거래 이력·변화 파일) | 서버 관리 없음. DynamoDB 시점 복구, S3 버전 관리로 백업 |
| 데이터 빌드 | 지금처럼 GitHub Actions(Node 버전은 Lambda와 같이 24로 올림) | 첫 수집이 1~2시간이라 Lambda 15분 제한에 맞지 않음. Actions는 OIDC로 받은 임시 역할로 S3에 접근(장기 키 없음) |
| 알림 발송 | 배포 확정 이벤트를 받는 Lambda + DynamoDB 대기 목록 + EventBridge Scheduler | 배포된 변화만 아침에 요약 발송. 발송 실패가 배포를 막지 않게 함 |
| 비밀값 | SSM Parameter Store | 웹 푸시 VAPID 키, 텔레그램 봇 토큰(6번을 할 때) |
| 배포 정의 | AWS SAM(코드로 관리) | 스택 하나로 재현·삭제 가능 |
| 프런트 | GitHub Pages 유지. 11번(정적 페이지)에서 S3 + CloudFront 이전 검토 | 지금은 옮길 이유가 없음 |

- EC2·EKS 대신 Lambda를 쓰는 이유: 짧은 요청과 하루 1회 발송 위주라 사용량 과금이 유리하고, OS 패치·TLS·재시작 같은 운영이 없다. EKS는 관리비만 월 약 $73이고 이 규모에 과하다. 텔레그램 봇은 상시 프로세스가 필요 없는 웹훅으로 받는다. 분석을 SQL로 자유롭게 해야 하거나, 데이터 빌드를 AWS로 옮기거나(이 경우 ECS Fargate 예약 작업), 꾸준한 트래픽으로 Lambda 비용이 서버 한 대 값을 넘으면 해당 부분만 옮긴다.
- 비용은 지금 규모에서 월 수 달러 수준으로 예상하지만 사용량을 보고 확인한다. AWS Budgets 알림(예: 월 $20)을 첫 작업에 포함한다.
- API는 Pages 출처만 CORS 허용, API Gateway 요청 제한, 요청 크기·관심 목록 개수 상한을 둔다.
- 모니터링: Lambda 오류율·발송 실패를 CloudWatch 알람으로 받는다. 서버 장애 시 프런트는 동기화·알림 기능만 숨기고 나머지는 그대로 보여 준다.

| 12 | 정책 2차: "현재 적용 중" 규제 배지 | 2~3일 | 토지거래허가구역·규제지역 등을 지역 상세에 표시. 종료일 관리 | 해제·변경을 따라가는 관리 부담이 커서 1차 운영 뒤 |

1~5번 구현은 약 3주 걸렸다(10-15 ~ 10-24). 5-1번 1단계와 9번은 10-25에 끝났다. 6번을 건너뛰었으므로 8번에서 알림 기반(대기 목록·발송 Lambda)까지 만들어 8번이 약 1주 늘어나고, 7~9번 구현은 약 4주로 본다. 기준선 관찰과 1차 점검의 대기 기간은 구현 기간과 별개다. 7~9번은 점검 결과에 따라 착수 여부와 범위를 정한다.

## 세부 사항

### 2. 측정

이벤트: 검색, 단지 조회, 관심 저장, 변화 확인, 후보 비교, 공유 링크 열기, 알림 연결·해지, 알림에서 들어온 방문, 재방문. 검색 원문과 상세 관심 목록은 수집하지 않는다.

- 브라우저마다 무작위 기기 ID(`crypto.randomUUID`)를 localStorage에 만들어 이벤트와 함께 보낸다. 쿠키·IP 저장·외부 분석 도구는 쓰지 않는다.
- 원본 이벤트에 기기 ID·이벤트 ID·서버 수신 시각·행동 종류·측정 정의 버전을 기록한다. 기기별 첫 방문·활성화 시각과 방문 날짜별 행동 요약을 유지하고, 매일 집계 Lambda가 활성화 시점 기준 7~13일·28~34일 코호트 표를 만든다. 관찰 구간이 끝난 기기만 분모에 넣는다. 원본 이벤트는 90일 뒤 자동 삭제(DynamoDB TTL)한다. 기기별 요약의 TTL은 마지막 활동 기준 90일로 매번 연장하고, 브라우저도 첫 방문일을 localStorage에 두고 이벤트와 함께 보내 요약이 지워진 뒤 돌아온 기기를 신규로 세지 않는다. 기기를 식별할 수 없는 집계만 장기 보관한다.
- 인증 없는 공개 API이므로 이벤트 ID로 중복을 제거하고, 기기 ID·IP 단위 요청 제한(IP는 제한 판정에만 쓰고 저장하지 않음)과 이벤트 종류 허용 목록을 둔다. 비정상적으로 많은 이벤트를 보낸 기기는 집계에서 제외한다.
- 개인정보처리방침에 기기 ID의 목적·보관 기간과 "이 기기 기록 삭제" 방법을 밝힌다.

지표:

- **활성화**: 첫 방문 후 24시간 안에 관심단지를 저장하고 그 요약을 확인한 기기 비율. 이 정의는 계속 유지한다. 4번 이후에는 평형까지 저장하고 요약을 확인한 비율을 별도 지표로 추가해 기존 기준선과의 비교를 보존한다.
- **핵심 재방문**: 활성화한 기기 중 다음 주(활성화 후 7~13일)에 관심단지 변화나 후보 비교를 확인한 비율. 28~34일 구간도 따로 잰다. 정확히 7일째 방문하는 지표와 구분한다.
- **변화 확인**: 새 거래가 있는 관심 사용자 중 변화 상세를 확인한 비율. 브라우저가 관심 목록과 변화 파일을 대조해 `watch_change_available` 이벤트를 보내고, 같은 변화 묶음의 상세 확인 이벤트와 연결한다. 상세 목록 대신 변화 묶음 ID·유무·건수만 수집한다. 사이트에 방문해 변화 유무를 확인한 기기만 분모로 삼으므로 미방문자의 변화 발생률과 구분한다.
- **알림 효과**: 알림 연결 비율, 알림 발송 후 24시간 안 방문 비율, 해지율. 채널(텔레그램·웹 푸시)과 알림 종류(새 거래·신고가·급등)별로 나눠 본다.
- **보조 지표**: 화면 종류별 조회, 비교 완료, 공유 링크 수신자의 관심 저장, 데이터 오류 제보.

첫 2주를 기준선으로 삼고 목표치를 정한다. 관심단지 수, 새 거래 유무, 알림 연결 여부, 모바일/데스크톱별로 나눠 본다. 동기화 코드를 쓰는 사람은 여러 기기를 한 사람으로 묶어 볼 수 있지만, 나머지는 기기 단위라 기기 변경·저장소 삭제 시 재방문이 낮게 나온다. 트래픽이 적은 동안은 A/B 수치만으로 결론 내리지 않고 실제 사용 관찰과 함께 평가한다. 코호트 정의는 [Amplitude의 리텐션 분석](https://www.amplitude.com/docs/analytics/charts/retention-analysis/retention-analysis-build)을 참고했으며 해당 제품 도입을 전제하지 않는다.

검증할 가설:

- 첫 방문 안내가 관심 저장을 늘린다.
- 변화 요약이 다음 주 확인을 늘린다.
- 개인 알림이 다음 주 확인을 늘리고, 해지율은 낮게 유지된다.
- 급등 알림이 들어온 방문을 늘리되, 해지율을 높이지 않는다(너무 자주 울리면 기준을 높인다).
- 같은 평형 비교가 후보 재확인을 늘린다.

### 3. 새 거래 판정 보완

- 브라우저의 계약일 비교 대신, 빌드에서 이전 이력 대비 새로 들어온 거래를 계산하고 최초 관측 이력을 유지한다. 최초 관측 시점은 신고일과 다르므로 화면에는 "새로 확인된 거래"로 표시한다.
- 이력과 변화 파일은 S3(버전 관리 켬)의 빌드 ID별 경로에 보관한다. 빌드 시작 때 마지막 확정 이력을 읽고 새 버전을 준비하되, Pages 배포 성공 뒤 해당 빌드의 확정 포인터를 갱신하고 발송 대상을 등록한다. 실패한 배포는 확정하지 않고 다음 빌드에서 다시 비교한다. 읽지 못하면 변화 판정 불가를 표시하고 알림을 보류하며 이력을 새로 만들거나 갱신하지 않는다. 잘못 쓴 이력은 이전 버전으로 되돌린다. 확정 작업 실패는 재시도·알람 대상으로 둔다.
- 비교 단위는 지역·거래 종류·계약월이다. 지금 빌드의 `fetchAll`(`scripts/build.js`)은 `getMonth`가 실패하면 catch에서 빈 배열을 돌려주고 `chunks.flat()`으로 합치므로, 수집 실패와 실제 거래 0건을 구분할 수 없다. 먼저 `fetchAll`이 월별 `{ ym, ok, rows }` 형태로 성공·실패 상태(와 마지막 성공 수집 시각)를 보존해, 합치기 전에 그 상태를 이력 비교 단계에 넘기게 바꾼다. 캐시만 읽는 `cachedMonth`는 운영 빌드가 쓰지 않으므로 대상이 아니다. 그런 다음 실패 구간은 삭제로 판정하지 않고 이전 이력을 유지한다. 조회 기간에서 빠진 월도 거래 삭제로 표시하지 않는다. 성공한 구간에서만 추가·삭제를 계산한다. 신고가·국면처럼 여러 월을 참조하는 지표는 계산에 필요한 구간이 모두 성공했을 때만 변화로 확정한다.
- 변화마다 안정적인 변화 ID를 부여하고 빌드 ID를 기록한다. 재시도와 중복 이벤트가 같은 변화를 다시 발송하지 않도록 하며, 지연된 이벤트가 최신 확정 포인터를 되돌리지 않게 버전을 확인한다.
- 배포 전 확인: `deploy.yml`의 워크플로 단위 `concurrency: pages`(진행 중 취소 없음)로 실행 전체가 직렬화된 상태에서, `deploy` job은 Pages 배포 전에 OIDC 역할로 현재 확정 포인터를 읽어 아티팩트 순번과 비교한다. 아티팩트 순번이 포인터보다 작으면(최신 확정 뒤 과거 실행을 재실행한 경우) Pages 배포와 확정을 모두 건너뛰고 알람을 보내며, Pages와 S3 모두 기존 최신 버전을 유지한다. 같으면 확정 재시도로 보고 진행한다. 포인터를 읽지 못하면 배포하지 않고 실패로 끝내 기존 사이트를 유지한다.
- 확정 단계: `deploy` job에서 Pages 배포가 성공하면 같은 job의 다음 단계가 OIDC 역할로 S3 확정 포인터를 갱신하고 확정 마커를 쓴다. main 푸시로 하루에 여러 번 배포될 수 있으므로 포인터는 빌드 순번이 더 클 때만 조건부로 갱신한다. 확정 단계는 환경 변수가 아니라 배포 아티팩트에 기록된 빌드 순번과 내용을 그대로 쓴다. 현재 포인터가 이미 같은 빌드 순번이면(포인터 갱신 뒤 마커 쓰기 전에 실패한 재시도) 성공으로 취급하고 빠진 확정 마커를 다시 쓴다. 마커 쓰기는 같은 경로에 같은 내용을 쓰는 멱등 작업이고, 마커를 받는 쪽은 변화 ID 조건부 등록으로 중복을 막는다. 배포 전 확인을 통과했더라도 확정은 계속 조건부로 하고, 그 사이 포인터가 더 큰 빌드 순번이 됐으면 이 빌드는 확정하지 않고 알람을 보낸다.
- 브라우저 쪽 데이터: 같은 날 여러 번 배포될 수 있으므로 비교는 날짜가 아니라 빌드 순번으로 한다. 빌드 순번은 데이터를 수집·빌드한 실행마다 새로 매기는 (`run_number`, `run_attempt`) 순서쌍이고 사전식으로 비교한다. `run_number`는 워크플로를 재실행해도 바뀌지 않으므로 단독으로 쓰지 않는다. 빌드 job이 순번을 아티팩트 메타에 기록하고, 이후 단계는 그 값을 읽는다. 전체 재실행("Re-run all jobs")은 데이터를 다시 수집하므로 새 `run_attempt`로 새 순번이 되고, 배포·확정 job만 재실행("Re-run failed jobs")할 때는 원래 아티팩트를 재사용하므로 순번과 내용이 그대로다. 오래된 실행을 전체 재실행해 더 큰 순번이 이미 확정돼 있으면 배포 전 확인에서 걸러 배포·확정을 모두 하지 않는다. 배포 거래 데이터에 거래별 최초 관측 빌드 순번을 필드로 추가하고(화면에 보여 줄 날짜는 메타 파일의 순번별 빌드 날짜 표로 구함), 메타 파일에 현재 확정 빌드 순번과 날짜를 넣는다. 이력을 처음 만들 때 이미 있던 거래는 최초 관측 순번을 비워 새 거래로 표시하지 않는다. 브라우저는 관심 항목마다 마지막으로 확인한 빌드 순번을 저장하고, 그보다 최초 관측 순번이 큰 거래를 "마지막 확인 이후 새로 확인된 거래"로 보여 준다. 따라서 여러 날 만에 방문해도 빌드별 변화 파일을 모을 필요가 없다. 삭제된 거래는 최근 30일 변화 목록(`changes-30d.json`)으로 따로 보여 준다. 필드 추가로 늘어나는 데이터 크기를 확인한다.
- 데이터 공급원의 거래 식별자를 먼저 확인한다. 매매 자료에 단지 고유번호가 없으므로, 없으면 단지·계약일·면적·층·금액으로 비교하되 조건이 같은 실제 복수 거래는 개수로 보존한다. 단지명 정규화(`canonicalKey`)를 거친 키를 쓴다.
- 처음 이력을 만들 때 기존 거래 전체를 새 거래로 표시하지 않는다.
- 취소·정정은 정확히 연결할 근거가 없으면 추가·삭제로만 표시하고 정정으로 단정하지 않는다.
- 반영 범위의 한계: `lib/molit.js`는 이번 달 기준 2개월 전까지 매매·전월세를 12시간마다, 12개월 전까지 매매를 1주일마다 다시 받는다. 그보다 오래된 매매와 2개월 전보다 오래된 전월세는 캐시가 있으면 재조회하지 않아 해제·정정을 놓칠 수 있다. 화면에 범위를 밝히고, 기간을 늘릴지는 API 호출 한도를 보고 정한다.
- 기존 사용자 전환: 브라우저의 `seen`(마지막 계약일)은 전환 시 버리고, 전환 후 첫 방문 때 현재 확정 빌드 순번을 마지막 확인 순번으로 저장해 그 시점부터 다시 시작한다. 전환 첫날 늦은 신고가 한꺼번에 새 거래로 뜨지 않게 한다.
- 구현 (3번): 이력은 `data/cache/ledger/`(`lib/ledger.js`)에 두어 원본 캐시와 같은 S3 스냅샷으로 보관·확정한다. 대상은 매매만이고 전월세는 아직 비교하지 않는다. 빌드 번호는 `run_number × 100 + run_attempt`(재실행 50회 제한으로 순서 보존), 지역 데이터의 매매 행 끝에 처음 확인한 빌드 번호를 붙인다(이력 시작 전 거래는 생략). 이번 달(신고 진행 중) 매매도 지역마다 받아 이력·피드·관심단지·단지 화면 최근 매매·지역 화면 단지 목록(최근 1년 거래 수와 최근 거래일만)에 '이번 달 · 신고 진행 중'으로 표시하고, 지역 지표·예측·차트·시세에는 넣지 않는다(지역 데이터 파일에는 들어 있고 화면이 조회 기간 밖 거래로 구분). 그래서 이번 달 계약이 신고되는 날 새로 확인된 거래로 잡히고, 월이 바뀌어도 한꺼번에 몰리지 않는다. 국토부 호출은 빌드마다 지역 수(51)만큼 늘고 12시간 캐시를 쓴다. 이번 달 수집 실패는 `meta.missing`이 아니라 `meta.partial.missing`에 둬서 후보 점수·예측을 막지 않는다. 이력보다 새 계약월이 들어오는 경우(이력 시작 직후 등)에는 그 달 거래가 모두 새로 확인된 거래가 되고 피드에 안내를 띄운다. 거래 키의 단지명은 원본 명칭이라 대표 단지 별칭이 바뀌어도 대량 삭제·추가로 기록되지 않는다. 이력 시작 때 수집에 실패한 달은 나중에 받아도 기존 거래로 두고, 새로 들어온 달이 실패하면 다음 성공 때 새로 들어온 달로 본다. 국면 변화는 기준월(완성월)이 바뀔 때만 지난 기준월의 마지막 국면과 비교한다(같은 달 안 깜빡임 방지). 변화 파일은 `data/changes.json`(KST 같은 날 빌드의 변화를 모은 피드. 지역마다 신고가·급등 거래는 모두, 나머지는 최근 계약 30건만 담고 건수는 지역별 집계로 센다), `data/changes-30d.json`(삭제·급등·국면)이다. `meta.json`의 빌드 날짜 표는 최근 90일만 둔다. 모든 거래에 번호가 붙어도 지역 데이터는 gzip 기준 약 2% 커진다(17.4MB → 17.7MB).
- 검증 사례: 늦은 신고, 같은 계약일, 정정, 취소, 중복 수집, 특정 지역·월 수집 실패와 복구, 실제 거래 0건인 월, 조회 기간 이동, 이력 읽기 실패, 배포 실패, 확정 작업 재시도, 포인터 갱신 직후 실패한 뒤 같은 빌드의 확정 재시도, 같은 날 복수 배포 후 재방문(오전 배포 확인 뒤 오후 배포의 새 거래 표시), 확정된 실행을 전체 재실행한 뒤 새로 수집된 거래 표시, 배포 job만 재실행할 때 같은 순번·같은 내용 유지, 최신 확정 뒤 과거 실행 재실행 시 Pages와 S3 모두 기존 최신 버전 유지, 배포 전 포인터 읽기 실패.

### 3-1. 급등 판정

이미 신고된 거래와 공개 지수로 "최근 크게 올랐다"를 판정한다. 앞으로의 가격을 예측하지 않는다. 3번의 변화 생성 단계에서 함께 계산하고, 수집에 실패한 구간이 계산에 걸리면 판정하지 않는다.

- **단지 급등** (관심단지·평형 대상): 새로 확인된 매매 거래가 같은 평형의 직전 6개월 거래 중위값보다 10% 이상 높고, 그런 거래가 최근 60일 안에 2건 이상이거나 기간 내 최고가를 5% 이상 넘었을 때. 직전 6개월 거래가 3건 미만이면 기준이 불안정하므로 판정하지 않는다. 직거래와 1~2층 거래는 기준 거래에서 뺀다. 높은 거래 1건만 있으면 급등이 아니라 "높은 가격 거래"로만 표시한다.
- **지역 급등** (♥ 지역·관심단지가 있는 지역 대상): 부동산원 주간 매매지수가 2주 연속 주 0.3% 이상 오르거나, 구성 보정 평당가의 3개월 변화(완성월 기준)가 +3% 이상일 때.
- 기준값은 초안이다. 착수 시 과거 60개월 데이터로 단지·지역별 발생 빈도를 계산해, 관심단지 하나에 평균 분기 1회를 넘지 않도록 조정하고 결과를 이 문서에 기록한다. 이후 가격 경로도 함께 기록하지만 예측력의 근거로 쓰지 않는다.
- 단지 급등 점검 결과 (2026-10-18, `scripts/surge-frequency.js`, S3 확정 이력의 2021-10~2026-09 매매, 5년간 거래 10건 이상인 6,644개 단지, 거래를 계약일에 확인했다고 가정): 상승 기준 +10%에서 단지당 분기 평균 0.13회, 상위 10% 단지 0.39회, 분기 1회를 넘는 단지 0.8%. +8%는 평균 0.19회(초과 2.8%), +12%는 0.09회(0.3%). 목표를 만족하므로 초안(+10%)을 유지한다. 판정된 거래 중 18.5%는 1건뿐이라 "높은 가격 거래"로만 표시된다. 지역 급등(주간지수·3개월 평당가) 빈도는 아직 재지 않았다. 1차 점검 때 실제 발생 빈도와 함께 다시 본다.
- 같은 단지·평형(또는 지역)의 급등 알림은 30일에 한 번만 보낸다. 조건이 풀렸다가 다시 충족되면 새 알림으로 본다.
- 화면: 첫 화면 피드와 관심단지 요약에 "급등" 배지와 판정 근거(기준값, 상승률, 기준 거래 수)를 표시하고, "과거 거래 기준이며 앞으로의 가격을 뜻하지 않음" 안내를 붙인다.
- 검증 사례: 거래가 드문 단지, 직거래·저층 고가 거래, 높은 거래 1건, 수집 실패 구간 포함, 같은 조건 반복 충족(30일 제한), 늦게 신고된 고가 거래.

### 4. 첫 방문 안내와 관심 평형

- 구현 (4번): 관심단지가 하나도 없으면 개요 위와 빈 관심단지 화면에 3단계 안내(단지 검색 → 평형 고르고 ★ 저장 → 관심단지에서 확인)를 보여 준다. '검색하기'는 상단 검색창으로 옮기고, 닫으면 그 브라우저에서는 다시 띄우지 않는다(`homeTrend.guideOff`). 가입 없이 브라우저에 저장된다는 점을 함께 밝힌다.
- 단지 화면의 ★는 지금 고른 전용면적을 관심 항목의 `area`(`areaKey` 값)로 저장한다. 저장 뒤에는 다른 면적을 골라 관심 평형을 바꿀 수 있고, 면적 버튼에 ★로 표시한다. 고를 수 있는 면적은 조회 기간에 거래가 있었던 면적이며, 기간을 늘리면 더 오래전 면적도 보인다고 안내한다. 지역 화면 단지 목록의 ★는 평형 없이 저장해 지금처럼 주력 평형으로 요약한다.
- 관심단지 요약·비교 차트·첫 화면의 '관심단지에 새 거래' 알림은 관심 평형 기준이다. 새 거래·신고가·급등·삭제는 그 평형만 세고, 다른 평형의 새 거래는 건수만 한 줄로 보여 준다. 관심 평형이 최근 3년 매매에 없으면 주력 평형으로 요약하고 그 사실을 밝힌다.
- 측정 (버전 2): `watch_add`에 관심 평형까지 저장했는지(`a`), `watch_area`(관심 평형 저장·변경), `guide`(`show`·`search`·`close`)를 더한다. 어떤 평형인지는 보내지 않는다. 기기 요약에 `firstWatchAreaAt`, `activatedAreaAt`을 두고, 기존 활성화 정의는 그대로 둔 채 '평형까지 저장한 활성화'를 activation 표의 `area`로 따로 센다. 분모는 버전 2 이후 처음 온 기기(`firstV`)만이라 기존 기준선과 섞이지 않는다.

### 5. 동기화 코드

- 코드는 128비트 무작위 값이고, 서버에는 해시만 저장한다. 코드를 아는 사람은 목록을 읽고 고칠 수 있으므로 링크 공유 주의 문구를 표시하고, 재발급하면 이전 코드는 무효가 된다.
- 동기화 데이터에 형식 버전과 서버 리비전을 둔다. 클라이언트는 읽었던 리비전과 항목별 변경을 보내고, 서버는 조건부 갱신으로 동시 쓰기를 감지한다. 서로 다른 항목의 변경은 병합하되 같은 항목 충돌은 현재 서버 값을 보여 주고 사용자가 다시 적용하게 한다. 기기 시각으로 최신 변경을 결정하지 않는다.
- 삭제 표시는 서버에서 90일 보관한다. 90일 이상 동기화하지 않은 기기는 서버 목록을 먼저 다시 받고 로컬 미반영 변경을 사용자에게 확인받은 뒤 적용한다. 오래된 전체 목록으로 서버를 덮거나 삭제된 항목을 자동 복원하지 않는다.
- 브라우저 목록이 먼저 저장되고 서버는 나중에 맞춘다. 오프라인·서버 장애 때도 저장은 실패하지 않는다.
- 1년간 접근이 없는 코드와 목록은 삭제하고, 사이트에서 즉시 삭제할 수 있게 한다.
- 구현 (5번): `POST /sync/{op}`(`infra/functions/sync/`). `create`(새 코드 + 이 기기 목록), `push`(변경 보내고 서버 목록 받기, 변경이 없으면 받기만), `rotate`(재발급, 이전 코드는 같은 트랜잭션에서 삭제), `delete`. 코드는 주소가 아닌 본문으로만 받고, Crockford base32 26자로 보여 주며 옮겨 적을 때 대소문자·하이픈·헷갈리는 글자를 무시한다. DynamoDB 항목 하나(`pk sync#<SHA-256>`)에 형식 버전·서버 리비전·항목별 리비전을 두고, 읽은 리비전일 때만 쓰는 조건부 쓰기로 동시 쓰기를 감지한다.
- 항목: 관심단지 `w:<지역>:<단지 키>` = 이름·지번·지역·관심 평형·조회 기간(단지 화면에서 고른 기간을 관심 항목의 `months`로 기억), 좋아요한 지역 `r:<지역>`. 마지막 확인 빌드(`checked`)는 기기마다 따로 둔다. 클라이언트는 마지막으로 받은 서버 목록(`homeTrend.sync`의 `snap`)과 지금 목록의 차이를 항목 리비전(`from`)과 함께 보낸다. 서버 값의 리비전이 `from`과 다르면 충돌로 돌려주고 서버 값을 유지한다. 결과가 이미 같거나, 양쪽 모두 없다고 보는 항목을 추가하면 충돌로 보지 않는다.
- 사용자 확인(`homeTrend.syncHeld`): 충돌은 서버 값을 보여 주고 '다시 적용'으로 지금 리비전에 다시 보낸다. 삭제 표시를 지울 때 가장 큰 리비전을 `purged`로 남기고, 그보다 오래된 리비전으로 보낸 변경은 적용하지 않고 서버 목록을 돌려준다(90일 규칙을 기기 시각 없이 판정). 링크로 연결할 때 이 기기에만 있거나 값이 다른 항목은 '합치기'를 묻는다.
- 연결은 링크(`#/sync/<코드>`, 연 뒤 주소에서 코드를 지움)·QR(누를 때만 qrcode-generator를 불러옴)·코드 입력. 저장 뒤 1.5초 모아 보내고, 페이지를 열 때·화면으로 돌아올 때(1분에 한 번)·네트워크가 돌아올 때 맞춘다. 서버 주소(`meta.api`)가 없으면 동기화 화면을 그리지 않고, 실패해도 브라우저 저장은 그대로다. 없어진 코드(재발급·삭제·만료)는 연결을 끊고 목록은 남긴다.
- 측정 (버전 3): `sync`(`create`·`link`·`rotate`·`delete`·`unlink`·`conflict`) 행동 종류만. 코드·목록은 보내지 않는다. 기존 지표 정의는 그대로다.

### 5-1. 매매/전세 보기 분리

- 처음에는 매매 판단을 위해 만들었지만, 매매만 보고 싶을 때는 매매만, 전세를 알아볼 때는 전세만 보도록 나눈다. 전세가율·갭은 두 보기에 모두 둔다.
- 1단계 (보기 전환, 완료: #29, 2026-10-25. 측정 Lambda를 먼저 배포한 뒤 머지했다): 데이터 파일 형식은 그대로 두고 화면에서 거른다. 지역 전세 지표는 `analyze.js`의 `jeonseIndicators`(전세 이동평균·전세 계약 수를 매매와 같은 계산에 넣음, 국면 없음)로 빌드 때 `indicators.jeonse`에 넣고, 개요 시계열에 `jeonseMa`를 더한다. 단지 목록은 `apartmentList(전세, 'deposit')`로 브라우저에서 만든다. 부동산원 주간 전세지수 1·12주 변화를 더한다. 전세 보기에서는 매매가 없는 단지도 전세 거래가 있으면 열린다. 측정 버전 4: 보기를 바꾼 행동(`deal`)과 전세 보기에서 일어난 방문·조회(`j`)만 보낸다.
- 2단계 (전세 변화, 1차 점검 뒤 착수 여부 결정, 약 1주): 거래 이력(`lib/ledger.js`)에 전세를 더해 새로 확인된 전세 거래·전세 최고가를 만들고, 첫 화면 피드와 관심단지 요약에 넣는다. 관심 항목에 매매용·전세용 구분을 둔다. 피드·관심단지 요약이 바뀌어 점검 결과와 섞이므로 점검 뒤에 한다.
- 3단계: 전세용 지표(전세 흐름 국면, 역전세 위험)와 월세·반전세 포함 여부. 13번의 '전세 위험 체크'와 합쳐 검토한다.
- 확인할 것: 전세 보기 사용 비율(`j`가 붙은 조회 기기 수), 전환 횟수. 사용이 적으면 2단계를 미룬다.

### 6. 개인 알림 (텔레그램은 선택)

- 상태 (2026-10-25): 6번은 건너뛴다. 아래 공통 규칙(발송 준비·발송·재시도·해지·검증 사례)은 8번 웹 푸시에서 구현하고, 텔레그램 연결·웹훅 항목은 나중에 다시 검토할 때를 위해 남겨 둔다.
- 채널: 텔레그램(6번)은 선택 작업이고, 사용자에게도 원할 때만 켜는 선택 항목(기본 꺼짐)이다. 아래 발송 준비·발송·재시도·해지 규칙은 채널과 무관한 공통 규칙으로 만들어 웹 푸시(8번)도 그대로 쓴다. 6번을 하지 않으면 텔레그램 연결·웹훅 항목만 빠진다.
- 알림 종류: 새로 확인된 거래, 신고가, 급등(세부 사항 3-1). 사용자가 종류별로 끄고 켤 수 있고, 급등만 받는 설정도 둔다.
- 텔레그램 연결(6번을 할 때): 사이트에서 "텔레그램으로 받기"를 누르면 일회용 토큰이 담긴 `t.me/<봇>?start=<토큰>` 링크를 연다. 봇이 토큰을 받아 대화 ID를 동기화 코드에 묶는다. 토큰은 10분 뒤 만료되고 한 번 쓰면 무효가 된다.
- 웹훅 검증: `setWebhook`에 `secret_token`을 지정하고, Lambda는 `X-Telegram-Bot-Api-Secret-Token` 헤더가 맞지 않는 요청을 거부한다. 같은 `update_id`는 한 번만 처리한다.
- 발송 준비: Pages 배포가 성공해 확정된 빌드의 변화 파일만 처리한다. 배포 확정 이벤트만 발송 준비를 시작한다. S3 이벤트를 쓰면 확정 마커 경로만 구독하며, 중복 전달·순서 역전에 대비해 이벤트가 가리키는 빌드 버전을 확인하고, 구독 ID·변화 ID를 키로 DynamoDB에 대기 항목을 조건부 등록한다.
- 발송: EventBridge Scheduler가 매일 오전 9시(KST)에 Lambda를 실행해 구독별 대기 변화를 한 메시지로 보낸다. 새벽 4시 빌드의 변화는 아침까지 보관하며, 변화가 없으면 보내지 않는다. 하루 최대 1회, 밤 시간 발송 금지. 당일 발송 이후 들어온 변화와 실패 항목은 다음 허용 시간까지 유지한다.
- 재시도: 발송 작업은 조건부 잠금과 발송 기록으로 중복 실행을 막는다. 일시 오류는 재시도하고, 차단이 확인된 경우만 구독을 삭제한다. 외부 발송 성공 뒤 기록 저장 전에 중단되면 결과가 불확실하므로 자동 재발송 대신 별도 상태로 남기고 알람으로 확인한다.
- 검증 사례: 새벽 배포, 같은 날 복수 배포, 중복·역순 이벤트, 배포 실패, 발송 실패와 재시도, 해지 후 대기 메시지 폐기.
- 메시지에는 단지·평형·금액·계약일과 사이트 링크만 넣는다. 급등 알림은 "급등" 표시와 함께 판정 근거(예: 6개월 중위값 대비 +12%, 기준 거래 2건)를 쓰고, "더 오른다" 같은 예측이나 매수 권유 표현은 넣지 않는다.
- 해지: 봇 `/stop`, 사이트 해지 버튼, 봇 차단이 확인되면 구독을 자동 삭제한다. 대기 목록도 함께 삭제하고 발송 직전에 구독 상태를 다시 확인한다.
- 텔레그램 대화 ID와 웹 푸시 구독 정보는 개인정보로 다루고 개인정보처리방침에 목적·보관 기간을 적는다. 해지 즉시 삭제한다.
- 카카오톡 알림톡은 사업자 등록과 건당 비용이 필요해 이용 규모를 본 뒤 검토한다. 이메일(SES)은 도메인 인증과 발송 한도 해제가 필요해 13번으로 둔다.

### 9. 정책 자료 형식

```json
{
  "id": "2026-xx-loan",
  "announced": "2026-xx-xx",
  "effective": "2026-xx-xx",
  "ended": null,
  "title": "…",
  "category": "대출 | 규제지역 | 토지거래허가 | 세제 | 공급",
  "regions": ["all"],
  "summary": "한두 줄 요약",
  "source": "정책브리핑·국토부·금융위 보도자료 URL"
}
```

- 발표일과 시행일을 구분한다. 차트 마커는 발표일 기준으로 표시한다.
- 해제·변경된 정책은 지우지 않고 `ended`를 채워 이력으로 남긴다.
- 페이지에 "요약은 참고용, 정확한 조건은 원문 확인" 안내와 마지막 수정일을 표시한다.
- 새 정책 후보는 정책브리핑·보도자료 RSS로 모을 수 있지만, 사람이 확인한 뒤 PR로 추가한다.
- 초기 내용: 최근 3~5년 주요 정책 초안을 공식 출처 기준으로 만들고 날짜·대상 지역을 검토한다.
- 구현 (9번): 파일은 `{ updated, items: [위 형식] }`이다. `regions`는 `all`(전국)·묶음 이름(`서울`·`경기`)·지역 코드를 섞어 쓴다. `lib/policies.js`가 날짜·분류·지역 코드·출처(https)·id 중복을 검사하고, 빌드는 수집 전에 검사해 틀리면 멈춘다(이전 배포 유지). 배포 파일은 `data/policies.json`, 로컬 서버는 `/api/policies`.
- 차트: 지역 평당가 차트와 단지 평형 차트에서 그 지역에 해당하는 정책을 발표한 달의 이동평균선 위에 ▼로 표시하고, 십자선이 그 달에 오면 설명 줄에 제목을 적는다(같은 달 여러 건은 '외 N건'). 이동평균이 없는 달(처음 몇 달·신고 진행 중인 달)은 표식 없이 설명 줄에만 나온다. '정책 발표' 칩으로 켜고 끈다. 매매·전세 보기 모두 같다.
- 타임라인: 상단 '정책' 탭(`#/policy`, 지역별 `#/policy/<코드>`). 분류 필터, 연도별 목록, 발표·시행·종료일, 대상 지역, 요약, 원문 링크, 마지막 수정일과 "요약은 참고용·인과 아님" 안내.
- 변화 파일: 이전 빌드까지 본 정책 id(`data/cache/ledger/policies.json`, 거래 이력과 같은 S3 스냅샷)에 없는 정책을 `policy` 변화로 만든다(`lib/changes.js` `policyChanges`). 이력 시작 때는 내지 않고, 지웠다가 다시 넣은 정책도 새 정책으로 보지 않는다. 첫 화면 피드에 대상 지역이 그 묶음에 걸리는 새 정책을 보여 준다. 최근 30일 목록과 알림(8번)에는 아직 넣지 않았다.
- 측정: 타임라인 조회는 측정 행동 종류에 없어 보내지 않는다(Lambda 배포가 먼저 필요해서 1차 점검 뒤 필요하면 더한다).
- 초기 자료 (2026-10-25): 2022-11 규제지역 해제부터 2026-08 주택 신속공급 방안까지 13건. 날짜·대상 지역은 정책브리핑·국토부·금융위·서울시 자료로 확인했고, 머지 전에 사람이 원문과 한 번 더 대조한다. 2022년 이전과 세제 정책은 아직 없다.

## 후순위

전국 확대, 커뮤니티, 예측 모델 추가, 유료화, 선택적 계정(이메일·소셜 로그인)은 관심 저장과 반복 확인이 검증된 뒤 판단한다. 계정은 동기화 코드 사용량과 요청을 보고 도입하며, 기존 동기화 코드 목록을 계정으로 옮기는 기능을 지원한다.
