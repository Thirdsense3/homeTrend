# 로드맵: 재방문 장치와 정책 정보

작성일: 2026-10-15. 현재 코드(정적 GitHub Pages, 로그인 없음, 관심 목록은 localStorage, 해시 라우팅, 방문 분석 없음)를 기준으로 한 작업 계획이다. 사용자 수·행동 데이터로 검증하기 전의 가설이며, 기간은 순서를 정하기 위한 대략치이고 확정 견적이 아니다.

## 제품 방향

서울·경기에서 매수나 이사를 준비하며 후보 단지를 반복 확인하는 사람을 첫 핵심 사용자로 삼는다. 핵심 가치는 "내가 보는 단지와 지역에 무엇이 바뀌었는지, 후보끼리 어떻게 다른지 빠르게 확인한다"이다.

첫 방문 → 관심단지·평형 저장 → 변화 확인 → 후보 비교 → 다음 변화 때 재방문하는 흐름을 만든다. 실거래는 신고 지연이 있고 단지별 거래도 드물므로 주간 확인을 기본으로 하되, 매일 갱신되는 변화와 월간 지역 흐름도 제공한다.

## 원칙

- 서버를 새로 두지 않는다. 매일 빌드(GitHub Actions)와 정적 파일로 할 수 있는 것부터 한다.
- 로그인 없이 쓰는 구조를 유지한다. 개인 데이터는 브라우저에 두고, 수집하는 정보는 최소화한다.
- 재방문 장치는 실제로 관측된 변화(새 거래, 신고가, 국면 변화, 새 정책)부터 알린다. "급등 알림" 같은 자극적인 장치는 만들지 않는다. 예측은 지금처럼 실험 표시와 검증 기준을 유지한다.
- 정책은 날짜와 원문만 보여 주고 "정책 때문에 올랐다/내렸다" 같은 인과 해석은 하지 않는다.
- 한 번에 핵심 흐름 하나씩 바꾸고 효과를 확인한다.

## 이미 있는 기반

- 로그인 없는 지역 좋아요·관심단지 저장, 지역·단지 검색.
- 관심단지의 새 거래·신고가 배지, 주력 평형 가격 비교 차트.
- 실거래·전세가율·거래량·주간지수·실험적 예측.
- GitHub Pages 정적 배포와 매일 데이터 갱신.

## 현재 빈틈

1. 방문 분석이 없어서 재방문율과 개선 효과를 알 수 없다.
2. 관심단지의 새 거래 표시는 사이트를 열어야만 보인다. 사이트 밖에서 알리는 수단이 없다.
3. 관심 목록이 브라우저에만 있어서 저장소를 지우거나 기기를 바꾸면 사라진다.
4. 해시 라우팅이라 지역·단지 페이지가 검색에 따로 노출되지 않고, 공유 미리보기도 모든 페이지가 같다.
5. 새 거래 판정 기준(`seen`)이 마지막 **계약일**이라서, 계약은 그 전에 했지만 늦게 신고된 거래가 새 거래에서 빠진다 (`public/app.js`의 관심단지 화면). 배포 거래 포맷에는 최초 관측 시점도 없다.
6. 첫 방문자에게 무엇부터 보면 되는지 안내가 없고, 관심단지는 평형 없이 단지 단위로만 저장된다.

## 세부 사항

### 1. 측정

이벤트: 검색, 단지 조회, 관심 저장, 변화 확인, 후보 비교, 공유 링크 열기, 재방문. 검색 원문과 상세 관심 목록은 수집하지 않는다.

쿠키 없는 분석은 같은 브라우저의 재방문을 구분하지 않으므로, 코호트는 브라우저 안에서 계산한다.

- 첫 방문일·활성화일을 localStorage에 기록한다(서버로 보내지 않음).
- 보낼 때는 식별자 없이 구간만 이벤트 이름에 붙인다. 예: `activate`, `revisit:d7-13`, `revisit:d28-34`. 같은 구간 이벤트는 브라우저당 한 번만 보낸다.
- 비율은 같은 기간의 `activate` 수 대비 구간 이벤트 수로 구한다. 저장소 삭제 시 새 브라우저로 잡혀 재방문이 낮게 나오는 쪽으로 오차가 생긴다.

- **활성화**: 첫 방문 후 24시간 안에 관심단지를 저장하고 그 요약을 확인한 브라우저 비율. 5번 이후에는 평형 저장까지 포함한다.
- **핵심 재방문**: 활성화한 브라우저 중 다음 주(활성화 후 7~13일)에 관심단지 변화나 후보 비교를 확인한 비율. 28~34일 구간도 따로 잰다. 정확히 7일째 방문하는 지표와 구분한다.
- **변화 확인**: 새 거래가 있는 관심 사용자 중 변화 상세를 확인한 비율.
- **보조 지표**: 화면 종류별 조회, 비교 완료, 공유 링크 수신자의 관심 저장, 데이터 오류 제보, 채널 구독·해지.

첫 2주를 기준선으로 삼고 목표치를 정한다. 관심단지 수, 새 거래 유무, 모바일/데스크톱별로 나눠 본다. 브라우저 단위라 기기 변경·저장소 삭제에 따른 오차가 있다. 트래픽이 적은 동안은 A/B 수치만으로 결론 내리지 않고 실제 사용 관찰과 함께 평가한다. 코호트 정의는 [Amplitude의 리텐션 분석](https://www.amplitude.com/docs/analytics/charts/retention-analysis/retention-analysis-build)을 참고했으며 해당 제품 도입을 전제하지 않는다.

검증할 가설:

- 첫 방문 안내가 관심 저장을 늘린다.
- 변화 요약이 다음 주 확인을 늘린다.
- 같은 평형 비교가 후보 재확인을 늘린다.

### 3. 정책 자료 형식

```json
{
  "id": "2026-xx-loan",
  "announced": "2026-xx-xx",
  "effective": "2026-xx-xx",
  "ended": null,
  "title": "…",
  "category": "대출 | 규제지역 | 토지거래허가 | 세제 | 공급",
  "regions": ["all"],
  "summary": "한두 줄 요약",
  "source": "정책브리핑·국토부·금융위 보도자료 URL"
}
```

- 발표일과 시행일을 구분한다. 차트 마커는 발표일 기준으로 표시한다.
- 해제·변경된 정책은 지우지 않고 `ended`를 채워 이력으로 남긴다.
- 페이지에 "요약은 참고용, 정확한 조건은 원문 확인" 안내와 마지막 수정일을 표시한다.
- 새 정책 후보는 정책브리핑·보도자료 RSS로 모을 수 있지만, 사람이 확인한 뒤 PR로 추가한다.
- 초기 내용: 최근 3~5년 주요 정책 초안을 공식 출처 기준으로 만들고 날짜·대상 지역을 검토한다.

### 4. 새 거래 판정 보완

- 브라우저의 계약일 비교 대신, 빌드에서 이전 배포 대비 새로 들어온 거래를 계산하고 최초 관측 이력을 유지한다. 최초 관측 시점은 신고일과 다르므로 화면에는 "새로 확인된 거래"로 표시한다.
- 데이터 공급원의 거래 식별자를 먼저 확인한다. 매매 자료에 단지 고유번호가 없으므로, 없으면 단지·계약일·면적·층·금액으로 비교하되 조건이 같은 실제 복수 거래는 개수로 보존한다. 단지명 정규화(`canonicalKey`)를 거친 키를 쓴다.
- 처음 이력을 만들 때 기존 거래 전체를 새 거래로 표시하지 않는다.
- 이전 상태 보관: 지금 빌드가 쓰는 `actions/cache`는 7일간 접근이 없거나 용량이 넘치면 지워져 이력이 초기화될 수 있으므로 쓰지 않는다. 빌드 시작 때 배포된 Pages에서 이력 파일(`history.json`)을 받아 이어 쓰고, 받지 못하면 그날은 변화 없음으로 배포한 뒤 다음 빌드에서 다시 시도한다(이력을 새로 만들지 않음). Pages 파일로 부족하면 `data` 브랜치 커밋(`contents: write` 필요)을 검토한다.
- 반영 범위의 한계: 실거래는 최근 2개월만 다시 받으므로(`lib/molit.js`), 그보다 오래된 거래의 해제·정정은 잡히지 않는다. 화면에 이 범위를 밝히고, 재조회 기간을 늘릴지는 API 호출 한도를 보고 정한다.
- 기존 사용자 전환: 브라우저의 `seen`(마지막 계약일)은 전환 시 버리고, 전환 후 첫 방문 시점의 이력 기준으로 다시 시작한다. 전환 첫날 늦은 신고가 한꺼번에 새 거래로 뜨지 않게 한다.
- 취소·정정은 정확히 연결할 근거가 없으면 추가·삭제로만 표시하고 정정으로 단정하지 않는다.
- 검증 사례: 늦은 신고, 같은 계약일, 정정, 취소, 중복 수집.

### 8. 외부 채널

- 텔레그램 봇 토큰은 저장소 Secrets에 두고, 토큰이 없으면 게시 단계만 건너뛴다(기존 ECOS·REB 키와 같은 방식).
- 관심단지별 개인 알림(이메일·웹 푸시)은 구독 저장과 발송 서버가 필요하고, 웹 푸시는 iOS에서 홈 화면 추가 시에만 동작한다. 실제 수요를 확인한 뒤 정적 기능과 별도로 설계하며 해지·중복 방지·빈도 제한을 포함한다.

## 후순위

전국 확대, 커뮤니티, 예측 모델 추가, 유료화, 선택적 계정 동기화는 관심 저장과 반복 확인이 검증된 뒤 판단한다. 계정 동기화는 백업 링크 사용량과 동기화 요청을 보고 도입하며, 기존 브라우저 목록 이전과 충돌 처리를 지원한다.
